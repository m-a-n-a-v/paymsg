# Ralph Progress Log
Started: 2026-02-10

## Codebase Patterns

### Core Type Design
- **Financial amounts**: Always use `rust_decimal::Decimal`, never `f64`, for precise arithmetic
- **Serde derives**: All public types need `Debug, Clone, PartialEq, Serialize, Deserialize`
- **Transparent serialization**: Use `#[serde(transparent)]` for newtype wrappers to avoid nested JSON
- **Error handling**: Use `thiserror` in libraries, `anyhow` only in binaries (CLI)

### Validation Patterns
- **BIC validation**: BIC8 (8 chars) and BIC11 with branch="XXX" both represent head office
- **IBAN validation**: Mod-97 algorithm requires processing large numbers in chunks to avoid overflow
- **Currency codes**: ISO 4217 format - exactly 3 uppercase letters

### Date/Time Handling
- **MT formats**: Use YYMMDD (assumes 20XX century) for SWIFT MT messages
- **MX formats**: Use ISO 8601 (YYYY-MM-DD) for ISO 20022 MX messages
- **Chrono traits**: Import `Datelike` for date methods, `Timelike` for time methods

### Workspace Structure
- 7 crates with clear dependency hierarchy: core → mt/iso20022 → validate → translate → cli
- Shared dependencies in workspace Cargo.toml with `workspace = true` references
- All crates use workspace-level version, edition, and metadata

## 2026-02-10 - PAYMSG-003 ✅ COMPLETE

**Status**: Fully implemented and passing all quality checks

### What was implemented:
1. Created comprehensive MT message block structures (blocks.rs):
   - **BasicHeader (Block 1)**: Parses application_id (F/A), service_id (01/21), logical_terminal_address (12 chars), session_number (4 digits), sequence_number (6 digits)
   - **ApplicationHeader (Block 2)**: Handles both Input and Output formats
     - Input: direction, message_type (3 chars), destination BIC (12 chars), priority (N/U/S)
     - Output: extracts sender BIC from MIR structure
   - **UserHeader (Block 3)**: Optional tag-value pairs stored in HashMap (108:MUR, 121:UETR, 119:STP, etc.)
   - **TextBlock (Block 4)**: Raw message body content (field parsing deferred to PAYMSG-004)
   - **Trailer (Block 5)**: Optional tags (CHK, TNG, PDE, etc.)
   - All blocks derive Debug, Clone, PartialEq, Serialize, Deserialize

2. Implemented MT message parser (parser.rs):
   - **MtMessage struct**: Container for all 5 blocks with optional block3 and block5
   - **Block extraction logic**: 
     - Scans for {1:, {2:, {3:, {4:, {5: patterns sequentially
     - Handles nested braces in blocks 1, 2, 3, 5 with depth tracking
     - Special handling for Block 4 which ends with -} instead of }
     - Properly handles optional blocks 3 and 5
   - **Line ending normalization**: Converts \r\n to \n for consistent parsing
   - **Block-specific parsers**:
     - Block 1: Fixed-length field extraction (25 chars total)
     - Block 2: Separate logic for Input (16 chars) vs Output (46+ chars)
     - Block 3/5: Regex-based tag-value pair extraction: \{([^:]+):([^}]*)\}

3. Comprehensive test coverage (24 tests total):
   - **Unit tests in parser.rs** (16 tests):
     - Individual block parser tests (parse_block1 through parse_block5)
     - MtMessage parsing tests for MT103, MT202, MT940 with/without optional blocks
     - Error handling test for missing mandatory blocks
   - **Integration tests** (8 tests in tests/integration_tests.rs):
     - Parses real MT files from ../paymsg-specs/testdata/mt/
     - Tests all 4 message types: MT103, MT202, MT940, MT942
     - Tests minimal_valid and full_valid variants
     - Tests handling of different line endings (\n vs \r\n)
     - Multiple file tests to ensure robustness

### Learnings for future iterations:
- **Block extraction strategy**: Sequential scanning for {N: patterns is more reliable than regex for MT messages because:
  - Blocks can have nested braces (especially in Block 3 and 5)
  - Block 4 has a special terminator (-}) that differs from other blocks
  - Need to track brace depth to handle nested structures correctly
- **Optional blocks**: MT messages don't always have blocks 3 and 5, so the parser must:
  - Scan for each block individually rather than assuming sequential presence
  - Use Option<T> for block3 and block5 in MtMessage struct
  - Validate mandatory blocks (1, 2, 4) are present
- **Block 2 formats**: Input and Output have completely different structures:
  - Input: I + msg_type(3) + dest_bic(12) + priority(1) = 17 chars minimum
  - Output: O + msg_type(3) + time(4) + MIR(28) + date(6) + time(4) + priority(1) = 47 chars
  - Extract BIC from different positions depending on format
- **Integration test path resolution**: Same pattern as PAYMSG-002:
  - Use CARGO_MANIFEST_DIR to navigate from crate dir up to workspace root
  - Then traverse to sibling ../paymsg-specs directory
  - Works correctly during `cargo test` from any directory
- **Line ending normalization**: Always normalize \r\n to \n at the start of parsing to simplify all subsequent logic
- **Tag-value parsing**: Regex pattern `\{([^:]+):([^}]*)\}` works well for both Block 3 and Block 5
- **Error messages**: Use PaymsgError::ParseError(String) tuple variant, not struct variant with message/location fields
