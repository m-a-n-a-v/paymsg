## Codebase Patterns

### Core Type Design
- **Financial amounts**: Always use `rust_decimal::Decimal`, never `f64`, for precise arithmetic
- **Serde derives**: All public types need `Debug, Clone, PartialEq, Serialize, Deserialize`
- **Transparent serialization**: Use `#[serde(transparent)]` for newtype wrappers to avoid nested JSON
- **Error handling**: Use `thiserror` in libraries, `anyhow` only in binaries (CLI)

### Validation Patterns
- **BIC validation**: BIC8 (8 chars) and BIC11 with branch="XXX" both represent head office
- **IBAN validation**: Mod-97 algorithm requires processing large numbers in chunks to avoid overflow
- **Currency codes**: ISO 4217 format - exactly 3 uppercase letters

### Date/Time Handling
- **MT formats**: Use YYMMDD (assumes 20XX century) for SWIFT MT messages
- **MX formats**: Use ISO 8601 (YYYY-MM-DD) for ISO 20022 MX messages
- **Chrono traits**: Import `Datelike` for date methods, `Timelike` for time methods

### Workspace Structure
- 7 crates with clear dependency hierarchy: core → mt/iso20022 → validate → translate → cli
- Shared dependencies in workspace Cargo.toml with `workspace = true` references
- All crates use workspace-level version, edition, and metadata

  - Default values with `#[serde(default)]`

1. Created comprehensive MT message serialization module (serializer.rs):
   - **MtMessage::serialize()**: Main method to convert parsed MT structs back to SWIFT MT text format
   - **Block 1 serialization**: Generates `{1:F01BANKBICAXXX0000000000}` format
     - Zero-pads session_number to 4 digits (0 → 0000, 123 → 0123)
     - Zero-pads sequence_number to 6 digits (0 → 000000, 456 → 000456)

     - Validates message_type (3 chars), BIC (12 chars), priority (1 char)
   - **Block 3 serialization**: Optional user header tags
     - Format: `{3:{108:TESTMUR}{121:UUID}}`
     - Sorts tags alphabetically for consistent output
     - Skips serialization if block is empty
   - **Block 4 serialization**: Text block with CRLF line endings
     - Format: `{4:\r\n:20:REF\r\n:32A:...\r\n-}`
     - Converts any \n to \r\n for SWIFT compliance
     - Ensures trailing dash (-) before closing brace
   - **Block 5 serialization**: Optional trailer tags
     - Format: `{5:{CHK:ABC}{TNG:}}`
     - Skips serialization if block is empty
   - All serialization functions return Result<String, PaymsgError>

### Learnings for future iterations:
- **Block 1 padding**: Session and sequence numbers must be zero-padded to fixed widths (4 and 6 digits respectively)
  - Use format!("{:0width$}", num) for zero-padding
  - Parse string to u32 first to validate it's numeric
- **Block 2 formats**: Input and Output have completely different structures
  - Input is simpler: just direction + msg_type + BIC + priority (17 chars)
  - Output is complex: includes timestamps and MIR (Message Input Reference) structure (47+ chars)
  - For now, Output serialization uses default values; a full implementation would need additional fields in ApplicationHeader struct
- **CRLF line endings**: SWIFT MT standard requires \r\n (Windows-style) line endings
  - Always convert \n to \r\n when serializing Block 4
  - Parser normalizes to \n for easier processing
  - Serializer converts back to \r\n for compliance
- **Block 4 terminator**: Block 4 is special - ends with `-}` instead of just `}`
  - Must ensure content ends with \r\n- before closing brace
  - This is different from all other blocks
- **Optional blocks**: Blocks 3 and 5 are optional
  - When empty or None, don't serialize them at all (return empty string)
  - This keeps messages minimal and compliant
- **Tag ordering**: For Block 3 and Block 5, sort tags alphabetically for deterministic output
  - Makes testing easier (consistent serialization)
  - Though SWIFT doesn't require specific order, consistency is good practice
- **Round-trip testing strategy**: Best way to validate serialization
  1. Parse original MT file
  2. Serialize to text
  3. Parse the serialized text again
  4. Compare the two parsed structures (should be identical)
  5. Normalize whitespace for content comparison (CRLF vs LF)
- **Amount formatting**: SWIFT MT uses comma as decimal separator (European convention)
  - ISO 20022 MX uses period (American convention)
  - Must convert between these in translation layer (future story)
- **Date formatting**: MT uses YYMMDD, MX uses YYYY-MM-DD ISO 8601
  - Current implementation assumes 20XX century for YY dates
  - Could add logic for 1900s if needed, but modern messages are 2000+
- **Field serialization**: For Block 4, content is stored as raw text in TextBlock
  - Could provide a helper to build Block 4 content from Vec<MtField>

### Learnings for future iterations:
- **Field 61 complexity**: The most complex MT field due to multiple optional components
  - Entry date detection is ambiguous: 4 digits could be MMDD entry date OR part of an amount starting with 0
  - Solution: Only treat 4 digits as entry date if immediately followed by D, C, or R (debit/credit mark)
  - This prevents misinterpreting "231115C015000,00" as having entry date "C015" instead of D/C mark "C" + amount "015000,00"
- **Field 86 structured codes**: Banks use proprietary formats with ?NN codes
  - Common codes: ?20 (description), ?21-?29 (continuation), ?30 (sender BIC), ?32 (sender name), ?60 (beneficiary account)
  - Parser extracts these into subfields (code_20, code_32, etc.) while preserving original text
  - Handles both structured and unstructured formats gracefully
- **Balance field unification**: All balance fields (60F, 60M, 62F, 62M, 64, 65) share the same format
  - Single parse_balance_field() method handles all variants
  - Format: [D|C]YYMMDDCCCAMOUNT
  - Differences are in semantic meaning (opening vs closing, final vs intermediate, booked vs available)
- **MT942 vs MT940 differences**:
  - MT942 is for intraday/interim reports (no opening/closing balances)
  - MT942 has :34F: (floor limit - only transactions above this are detailed in :61:)
  - MT942 has :13D: (date/time of report generation)
  - MT942 has :90D:/:90C: (total counts and sums of debits/credits, including below-floor-limit transactions)
  - MT940 has :60F:/:60M: and :62F:/:62M: (opening and closing balances)
  - Both share :61: (statement line) and :86: (information to account owner)
- **Field 25 vs 25P**:
  - Field 25: Simple account number (up to 35 chars)
  - Field 25P: BIC/Account format (BIC of institution + account number separated by /)
  - Both are mandatory, but only one should be present
- **Regex-free parsing**: Most MT statement fields use fixed-position or character-based parsing
  - More reliable than regex for financial data
  - Better error messages when parsing fails
- **Test data importance**: Real MT940/MT942 test files revealed edge cases
  - Multiple :61:/:86: pairs in sequence
  - Structured vs unstructured :86: content
  - Supplementary details on continuation lines in :61:
  - Entry date presence/absence ambiguity
- **Reversal indicators**: Field 61 supports RD (reversal of debit) and RC (reversal of credit) in addition to D and C
  - Important for handling transaction corrections and chargebacks
  - Parser must check for 2-char D/C marks before checking 1-char marks
- **HashMap subfield storage**: Flexible approach allows different fields to have different subfield sets
  - Some fields have date+currency+amount (balances)
  - Some have multiple references and codes (field 61)
  - Some have structured codes (field 86)
  - JSON serialization with skip_serializing_if automatically omits empty subfields

### Learnings for future iterations:
- **XML attribute syntax**: Use `@AttributeName` for attributes, `$text` for element text content
  - Example: `<IntrBkSttlmAmt Ccy="EUR">1000.00</IntrBkSttlmAmt>`
  - Maps to struct with `#[serde(rename = "@Ccy")] currency: String` and `#[serde(rename = "$text")] value: Decimal`

  - Must manually add namespace during serialization (replace in string or use proper serializer)

- **ISO 20022 naming conventions**: Use full element names from schema
  - Element names are CamelCase in XML: `GrpHdr`, `CdtTrfTxInf`, `IntrBkSttlmAmt`
  - Struct field names use snake_case with `#[serde(rename = "...")]`: `group_header`, `credit_transfer_transaction_information`
  - Keep struct names matching XML for clarity: `GroupHeader`, `CreditTransferTransactionInformation`
- **Complex nested structures**: ISO 20022 has deep nesting
  - Financial institution: BranchAndFinancialInstitutionIdentification > FinancialInstitutionIdentification > BICFI/Nm/PstlAdr
  - Party: PartyIdentification > Id > OrgId/PrvtId > Othr > GenericOrganizationIdentification > Id + SchmeNm
  - Account: CashAccount > Id > IBAN or Othr > GenericAccountIdentification
  - Each level needs its own struct definition
- **Optional vs required fields**: ISO 20022 has many optional elements
  - Group-level settlement date/amount often optional (can be at transaction level)
  - UETR is optional but recommended for tracking
  - Payment type information entirely optional
  - Instructed amount only present when different from settlement amount
  - All instructions, purpose, regulatory reporting, remittance info optional
- **Array fields**: Some elements can repeat
  - CdtTrfTxInf: Vec of transactions
  - ChrgsInf: Vec of charges
  - Intermediary agents numbered (IntrmyAgt1, 2, 3) but modeled as separate Option fields
  - InstrForCdtrAgt, InstrForNxtAgt, RgltryRptg: Vec of instructions/details
  - Unstructured remittance: Vec<String> for multiple lines
- **Amount types**: Two different amount types in pacs.008
  - ActiveCurrencyAndAmount: For settled amounts (IntrBkSttlmAmt, TtlIntrBkSttlmAmt)
  - ActiveOrHistoricCurrencyAndAmount: For instructed amounts (InstdAmt, charges)

- **Path resolution in tests**: Integration tests from `tests/` directory
  - CARGO_MANIFEST_DIR points to crate directory (crates/paymsg-iso20022)
  - Need to go up 3 levels to reach workspace parent, then navigate to sibling paymsg-specs
  - Pattern: `parent().parent().parent().join("paymsg-specs")`
- **Decimal parsing**: rust_decimal handles string amounts correctly
  - XML amounts are strings: "1000.00", "25000.00"
  - Serde automatically deserializes to Decimal using FromStr
  - No manual parsing needed in struct definitions
- **Round-trip testing strategy**: Best validation for serialization
  - Parse XML → serialize → re-parse → compare key fields
  - Full struct comparison difficult due to potential whitespace differences
  - Focus on comparing business-critical fields (IDs, amounts, parties)

### Learnings for future iterations:
- **Feature-gating strategy**: Use `#[cfg(feature = "...")]` to conditionally compile incomplete code while keeping repo compiling
  - Define features in Cargo.toml: `[features] incomplete = []`
  - Apply to modules: `#[cfg(feature = "incomplete")] pub mod name;`

- **pacs.008 structure completeness**: The simplified pacs.008 implementation from PAYMSG-007 prioritized getting basic parsing working
  - Trade-off: simpler structures easier to implement initially
  - Cost: additional fields needed for full translation support
  - Solution: Extend pacs.008 structures with all optional fields from ISO 20022 spec
  - Pattern: Make new fields Option<T> to maintain backward compatibility

- **MT field complexity**: MT103 has many field options (50K/50A/50F, 59/59A/59F, 57A/57B/57C/57D)
  - Each option has different structure and meaning
  - Translation must try options in order of likelihood (K most common, then A, then F)
  - Field parsing from PAYMSG-004 provides subfield extraction which helps significantly

- **Mapping file as specification**: mt103_pacs008.json is comprehensive (625 lines)
  - Covers all field mappings with transform types, directionality, data loss notes
  - Includes MT-only and MX-only field handling strategies
  - Essential reference for implementation - read fully before coding

- **BIC normalization**: Critical for interoperability
  - MT messages often use BIC8 (head office implied)
  - MX messages prefer BIC11 for clarity
  - BIC11 ending in "XXX" also means head office (equivalent to BIC8)
  - Conversion: BIC8 + "XXX" = BIC11, BIC11.ends_with("XXX") → BIC8

- **Date century handling**: SWIFT convention for YYMMDD format
  - YY >= 50 → 19YY (1950-1999)
  - YY < 50 → 20YY (2000-2049)
  - Current year 2026: most messages will be 20XX range
  - Future-proof for next 24 years, historical coverage back to 1950

- **Charge bearer codes**: Different lengths and slight semantic differences
  - MT: 3 letters (SHA, OUR, BEN)
  - MX: 4 letters (SHAR, DEBT, CRED, SLEV)
  - SHA = shared charges (both parties pay their bank's fees) - SEPA requirement
  - OUR = ordering customer pays all (debtor bears charges)
  - BEN = beneficiary pays all (creditor bears charges) - not allowed in SEPA
  - SLEV = service level (fallback to shared in reverse translation)

- **UETR importance**: Unique End-to-End Transaction Reference
  - UUID format in Block 3 tag 121
  - SWIFT gpi (global payments innovation) requirement
  - Used for payment tracking across correspondent banking chain
  - Priority for EndToEndId: UETR > Field 20 > default value
  - Mandatory in pacs.008, optional in MT103 (but recommended)

- **Party identification complexity**: Different structures for person vs organization
  - Field 50F/59F numbered lines indicate structured format
  - Line 4 (date of birth) → private person (PrvtId)
  - No line 4 → organization (OrgId)
  - Field 50A/59A BIC → organization identified by BIC (rare for individuals)
  - Field 50K/59 name+address → most common format

- **Address handling**: Different models between MT and MX
  - MT: Up to 4 lines of 35 chars (account + name + address mixed)
  - MX PostalAddress: Structured fields (StrtNm, BldgNb, PstCd, TwnNm, Ctry) OR AdrLine[] (up to 7x70 chars)
  - Best practice: Extract first non-account line as name, remaining as address
  - IBAN detection: Check if account starts with 2-letter country code + 2 check digits

- **Testing strategy**: Test conversion utilities independently first
  - Each utility has clear input/output contract
  - Unit tests validate all conversion scenarios
  - Integration tests require full message parsing + translation
  - Feature gating allows partial implementation to be tested

- **Decimal handling in amounts**: rust_decimal for precision
  - MT amounts: comma decimal separator ("1234567,89")
  - MX amounts: period decimal separator ("1234567.89")
  - rust_decimal::Decimal avoids floating-point precision errors
  - Conversion: simple string replace (comma ↔ period)

- **UUID generation for derived fields**: chrono + uuid crates
  - GrpHdr/MsgId: Generate UUID or use "MT103-" + field 20 value
  - GrpHdr/CreDtTm: Current timestamp in ISO 8601 format
  - GrpHdr/NbOfTxs: Always "1" for single MT103 message
  - These are derived fields with no MT103 equivalent

  - Some MT fields have no MX equivalent (fields 51A, 53*, 54*, 55* - correspondent banking routing)
  - Some MX fields require defaults (MsgId, CreDtTm, InstgAgt, InstdAgt from message envelope)
  - Track all data loss in warnings array with category and description
  - Allows user to review what information was lost or approximated
